## Confirmed defects corrected

1. The OAuth validator refreshed successfully but then called `users.getProfile`, which is not
   authorized by `gmail.send`. Google returned HTTP 403 `insufficientPermissions`. The validator
   now checks token metadata for the required scope and explicitly distinguishes OAuth validation
   from sender/inbox verification. No permissions were broadened.
2. Admin confirmation, rescheduling, and cancellation actions checked their individual send option
   but ignored global notification settings. They now honor both.
3. Receipt resend ignored the receipt-email setting. It now refuses delivery when disabled.
4. The internal reminder delivery endpoint did not recheck reminder settings. It now fails closed
   when disabled or when settings cannot be read.
5. Runtime settings read failures restored email-enabled defaults. The fallback now disables email
   channels rather than overriding a possibly disabled stored setting.
6. Admin removal deleted the appointment before sending cancellation. The email log then referenced
   a nonexistent appointment, violating its foreign key before Gmail could be called. Cancellation
   after removal now logs the booking reference as metadata without that invalid foreign key.
7. Google request errors could propagate request/credential material to callers that log exceptions.
   Gmail submission now propagates only a fixed message with an optional numeric HTTP status.

OAuth state validation, development-only authorization routes, token-file protections, and the
existing Gmail provider were preserved. No deployment or commit was performed.

## Settings, failures, duplicates, and data integrity

At verification time, confirmation, rescheduling, cancellation, receipt, and admin notification
settings were enabled. Reminder email and reminders overall were enabled with a two-hour lead time.
Stored settings were not changed. No admin-notification email was triggered, since that could target
a recipient outside the authorized test address.

`node scripts/test-email-safety.cjs` passed nine isolated tests. These execute application functions
with external dependencies replaced, covering enabled/disabled admin notifications, receipt
suppression, reminder suppression, failed-settings suppression, persistence of booking/rescheduling/
cancellation when sending fails, sanitization of Gmail failures and failed email logs, and suppression
of an already-sent reminder on a scheduler rerun. These failure-injection tests did not access live
business records or send email.

Each live scenario produced exactly one sent log; no duplicate submission was observed. Reminder
processing has a unique appointment/start/channel identity and claim checks. General transactional
email has no shared idempotency key, and reminders cannot guarantee exactly-once delivery if Gmail
accepts a message but the final sent-status update repeatedly fails. Explicit receipt resends are
intentional repeat sends. Concurrency and crash-recovery delivery were not certified by this run.

Two preexisting failed confirmation logs contained the `invalid_grant` category. Their full error
text was not printed, and the rows were preserved.

Eight disposable cancelled appointments were created across the two successful live runs. Cancelled
fixtures could not reserve real appointment slots or be picked up by the live reminder scheduler.
Their eight email logs and all eight appointment rows were removed using exact fixture ownership
checks. No customers, payments, sales, recurring series, or persisted receipts were created.
Before/after row hashes and exact ID sets matched for appointments, customers, payments, sales,
sale items, receipts, recurring bookings, appointment reminders, customer email logs, admin settings,
and notification settings. This verifies those existing tables remained unchanged during the tests;
it is not an assertion about every table in the database.
